REPL at the Core — Inside One Turn

Claude Code's architecture has a central loop in query.ts. Every turn flows through a four-stage Read · Eval · Print · Loop. The REPL owns the canonical message array in REPL.tsx — the single source of truth for the conversation's state. Each R / E / P / L header below introduces the substeps that belong to it; substeps inherit the colour of their parent letter. Click any substep to expand.

The invariant — every substep either reads from or writes to messagesRef.current. Permissions gate Tool Detection (inside Eval), the sandbox gates Tool Execution (inside Eval), compaction rewrites the array between iterations, and memory extraction is itself a Print-phase hook. The four pillars are all anchored to this one loop.

Pattern-Based Permissions

Claude Code's permission engine is a three-layer defense designed to make a deny rule like rm * survive every common bypass — wrappers, env-var prefixes, compound commands, substitutions, and shell trickery. The outer orchestrator is checkSemanticsDeny(); the layers below are the helpers it delegates to.

Bypass Comparison — deny rule rm *

Seven real attack patterns, how Claude Code stops each, and where OpenCode's tree-sitter-only approach falls short.

The takeaway — Layer 1's normalization (wrapper-stripping + env-var-stripping + compound splitting) is what makes deny rules robust. Layer 2 and Layer 3 are the safety net: when they can't prove a command is safe, they force a user prompt instead of silently allowing it.
02

Sandboxing

Permissions decide what the model is allowed to ask for. Sandboxing decides what the process can actually do once the command is running. On Linux, Claude Code uses bubblewrap to launch unprivileged containers — a secure jail around the tool-execution process with restricted filesystem access and limited privileges.

Hardcoded Baseline Policy

Independent of user config, the adapter always injects these into the sandbox policy (sandbox-adapter.ts:225–287):

  • allowWrite = ['.', getClaudeTempDir()] — only the project cwd + Claude's temp dir are writable by default. Everything else on the host FS is read-only.
  • denyWrite baseline:
    • All Claude settings files (user, project, managed) — settings.json, settings.local.json
    • .claude/skills/ dir (same privilege as .claude/commands, .claude/agents)
    • Bare-git-repo marker files (HEAD, objects, refs, hooks, config) — anti-escape defense
    • Managed-settings drop-in dir
  • Network → forced through socat proxy (seccomp + namespace)
  • Seccomp filter blocks dangerous syscalls

Contrast with OpenCode — OpenCode's security model is entirely permission-prompt based. No jail, no filesystem ACLs, no network scoping. If the user clicks "allow" on a malicious command, there's nothing underneath to catch it.

Compaction

The context window is finite; conversations aren't. Claude Code ships five distinct compaction modes, from surgical cache-edits that don't touch the LLM to full 9-section structured summaries. The right mode fires based on token thresholds, cache state, and whether recent activity has been tool-heavy.

Session Memory — The Secret Sauce

Phase A: Background Extraction sessionMemory.ts

A post-sampling hook runs after every API response on the main thread. The hook checks shouldExtractMemory() on every turn. Extraction triggers when both conditions are met:

sessionMemory.ts:168–170
const shouldExtract =
  (hasMetTokenThreshold && hasMetToolCallThreshold) ||
  (hasMetTokenThreshold && !hasToolCallsInLastTurn)

There's also an initialization threshold — extraction doesn't start until the conversation reaches a minimum token count.

When triggered, it spawns a forked subagent that:

  • Reads the current session memory file from disk
  • Gets an update prompt with the current notes embedded
  • Uses the Edit tool (and only the Edit tool) to update the markdown file

The subagent is sandboxed — it can only edit the memory file, nothing else:

Phase B: Using Session Memory at Compaction Time sessionMemoryCompact.ts

sessionMemoryCompact.ts — trySessionMemoryCompaction
/**
 * Try to use session memory for compaction instead of traditional compaction.
 * Returns null if session memory compaction cannot be used.
 *
 * Handles two scenarios:
 * 1. Normal case: lastSummarizedMessageId is set, keep only messages after that ID
 * 2. Resumed session: lastSummarizedMessageId is not set but session memory has content,
 *    keep all messages but use session memory as the summary
 */
export async function trySessionMemoryCompaction(
  messages: Message[],
  agentId?: AgentId,
  autoCompactThreshold?: number,
): Promise<CompactionResult | null> {
  if (!shouldUseSessionMemoryCompaction()) {
    return null
  }

  // Initialize config from remote (only fetches once)
  await initSessionMemoryCompactConfig()

  // Wait for any in-progress session memory extraction to complete (with timeout)
  await waitForSessionMemoryExtraction()

  const lastSummarizedMessageId = getLastSummarizedMessageId()
  const sessionMemory = await getSessionMemoryContent() // Reads the session memory file

  // No session memory file exists at all -> fall back to full compaction
  if (!sessionMemory) {
    logEvent('tengu_sm_compact_no_session_memory', {})
    return null
  }
  . . .
  // Calculate the starting index for messages to keep
  // This starts from lastSummarizedIndex, expands to meet minimums,
  // and adjusts to not split tool_use/tool_result pairs
  const startIndex = calculateMessagesToKeepIndex(
    messages,
    lastSummarizedIndex,
  )

Preserves recent messages (configurable: min 10K tokens, max 40K tokens, at least 5 text-block messages).

  • lastSummarizedIndex — The index of the last message that the session memory has already captured via background extraction. Everything at or before this index is considered "summarized" in the session memory file.
  • calculateMessagesToKeepIndex — The index of the first message to preserve as raw messages in the post-compaction context. This is always ≤ lastSummarizedIndex + 1, because it expands backwards from the boundary to meet the minimum thresholds.

04

Persistent Memory

Memory lives in ~/.claude/memdir/ as markdown files with YAML frontmatter. A background extractor writes them; findRelevantMemories() uses Sonnet to select up to five files per query and inject them into context.

The taxonomy is built around a single question: is this knowledge derivable from the current project state? Code patterns, architecture, file structure, and git history are all re-derivable — they are deliberately excluded. The four types below capture what the repository alone cannot tell you.

U
User
Who the user is — role, goals, responsibilities, expertise. Shapes how Claude tailors responses to the specific person it's working with.
Example: senior backend engineer, deep Go experience, new to React
F
Feedback
Guidance about how to approach work — what to avoid and what's already been validated. Records from both failure and success, so Claude doesn't drift away from approved patterns while avoiding past mistakes.
Example: integration tests must hit a real DB — mocked tests masked a broken migration last quarter
P
Project
Ongoing work, initiatives, bugs, incidents — the why behind the current work that isn't visible in code or git history. The motivational context.
Example: auth middleware rewrite is driven by legal/compliance around session token storage, not tech debt
R
Reference
Pointers to where information lives in external systems — Linear projects, Grafana dashboards, internal wikis. Memory of where to look, not what's there.
Example: pipeline bugs tracked in Linear project "INGEST"
